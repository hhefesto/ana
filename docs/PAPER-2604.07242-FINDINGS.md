# arXiv:2604.07242 — Weaves, Wires, and Morphisms: what it offers this repo

Vincent Abbott and Gioele Zardini, "Weaves, Wires, and Morphisms: Formalizing and
Implementing the Algebra of Deep Learning", [arXiv:2604.07242](https://arxiv.org/abs/2604.07242)
(v1 2026-04-08, v3 2026-08-12). Reference implementations
[pyncd](https://github.com/mit-zardini-lab/pyncd) (Python) and
[tsncd](https://github.com/mit-zardini-lab/tsncd) (TypeScript).

Reviewed 2026-08-13 against this repo at bpe100m, 16.8% into the production run.

**§8 is a separate review** of `deepseek-ai/deepseek-harness` and the Cordis paper behind
it, added 2026-08-14 — a different paper in a different field, filed here because it was
raised for the same reason (visible category theory) and answered the same way (measure
before assuming).

**Verification status.** Every claim below marked ✅ was checked first-hand against the
primary source (paper full text, or the package README) during this review. A research
fan-out was run first; its adversarial-verification stage failed twice on API rate
limits, so its claims were re-checked manually rather than trusted — a process that
**caught one substantive error**, see §5.

**Known gap:** independent critique could not be obtained. The TMLR peer reviews for the
predecessor paper sit behind a bot-verification screen on OpenReview
([forum RyZB4qXEgt](https://openreview.net/forum?id=RyZB4qXEgt)), and
["Towards a Categorical Foundation of Deep Learning: A Survey"](https://arxiv.org/abs/2410.05353)
would need a full-text read to say whether it assesses this line of work. Everything
below is therefore the authors' own account of their contribution plus my reading of it;
no third party's assessment is represented.

## 1. The short version

The paper is **notation and formalization with no measured result of any kind.** It has a
Results section (§6), and that section reports representational capabilities — a
DeepSeek-V3 encoding, a code package, autoalignment, configuration generation,
compilation to PyTorch, hypergraph manipulation, diagram generation — and **no runtime,
throughput, FLOP count, MFU, accuracy, or loss number anywhere.** ✅

For this repo specifically, three things follow immediately:

- It would **not** have caught the worst bug in this project's history — the CE pullback
  that produced a correct loss with a garbage gradient. That is a differentiation bug,
  and *this* framework does not formalize differentiation: `Para` appears only as prior
  work by others and as future work to integrate with. ✅ (The TMLR predecessor does
  treat backprop diagrammatically — see §5, this is the one place the lineage is stronger
  than it first appears.)
- It cannot diagnose the ~3% MFU problem. There is no cost model in this paper. ✅
- It says nothing about GLA. No mention of linear attention, gated linear attention,
  RNNs, or recurrent forms; transformers appear only as motivating examples. ✅

**Recommendation: adopt nothing from this paper into the codebase.** Read the sibling
papers instead (§4), and treat this one as background reading for the Agda spec's
eventual treatment of broadcasting (§3).

## 2. What this paper does *not* do

Stated plainly, because the temptation with a category-theory paper adjacent to your own
formal-methods work is to assume it must help.

| Claim | Status |
|---|---|
| Reports a speedup | **No.** No timings anywhere ✅ |
| Reports an accuracy/loss result | **No.** No model is trained ✅ |
| Contains a FLOP or memory-transfer cost model | **No.** That is arXiv:2412.03317 ✅ |
| Formalizes gradients / pullbacks / backprop | **No.** `Para` is cited prior work + future work ✅ |
| Targets a non-PyTorch backend | **No.** PyTorch is the only named backend ✅ |
| Says anything about linear or gated-linear attention | **No.** ✅ |
| Has a second independent implementation to read as a spec | **No.** tsncd "automatically generates diagrams from an algebraic description generated by pyncd"; it performs no compilation, algebraic manipulation, or differentiation ✅ |

## 3. Question 1 — what it offers over `Transformer/Specification.agda`

The genuine delta is **strides as first-class objects.**

The paper formalizes broadcasting as an *axis-stride category* whose morphisms are finite
affine maps on index spaces, `η(x) = Λ_η · x + v_η`, composed with an array-broadcasted
category over arrays `[X;P]`. That is index arithmetic and array-shape lifting — an
operational object, and a different one from a dependently-typed shape signature. (Section
structure ✅: Introduction / Encoding Mathematics / Categories / Array-Broadcasted Category
/ Key Operations / Results / Future Work.)

`FormalTransformer/Transformer/Specification.agda` and `FormalTransformer/Layout.hs`
between them carry **extents and offsets**, not strides. `namedLayout` produces
`Slice {name, offset, length, decay}` — a flat parameter vector cut into named runs. The
Agda spec constrains shapes; it does not describe how a logical index maps to a linear
address, because nothing in the Haskell reference forward needs it to.

Where that gap would bite is exactly where this repo has already been bitten: the
hand-written Futhark kernels, where a mis-lowered index map is precisely the failure
class. `backend/futhark/model.fut` must agree with `Layout.hs` on the *order* of
`walpha` inside a GLA block — a comment in `Layout.hs` says so explicitly ("the Futhark
offsets in model.fut follow this order exactly") — and that agreement is currently
maintained by hand and by comment.

**But the paper does not close that gap for us.** It offers a vocabulary for stating the
obligation, not a checker, and not one that speaks Futhark. The honest assessment is that
this is a *notation this project could borrow if it ever formalizes the
Haskell↔Futhark layout correspondence*, and nothing more concrete than that today.

## 4. Question 2 — the cost model, and where it actually lives

Not in this paper. The relevant work is
[arXiv:2412.03317, "FlashAttention on a Napkin"](https://arxiv.org/abs/2412.03317).

Verified first-hand ✅:

- Sections are Introduction / Diagramming Deep Learning Algorithms / Examples / Analysis
  of Performance Models / Pseudocode and Hardware Optimizations / Conclusions. **There is
  no Experiments or Evaluation section and no measured GPU wall-clock timing.**
- FLOP model: "A k-size contraction requires 2k FLOPs; therefore, m×k by k×n matrix
  multiplication requires 2mkn FLOPs."
- Transfer model: `H*(a⃗, M) = Σ_t α_t(a⃗) · M^(−β_t)` — total transfers as a sum of power
  functions of axis sizes and available fast memory `M`.
- The Conclusions state: **"The performance model and the hypothesized algorithm remain
  to be empirically validated."**

So the methodology is published and reproducible on paper, and its accuracy is **unknown
by the authors' own statement.**

### The one measured result in the lineage, and its important caveat

[arXiv:2505.09326](https://arxiv.org/abs/2505.09326), "Accelerating Machine Learning
Systems via Category Theory: Applications to Spherical Attention for Gene Regulatory
Networks" (Abbott, Kamiya, Glowacki, Atsumi, Zardini, Maruyama) reports **3.6× over
PyTorch and performance comparable to fine-tuned FlashAttention on an A100**, from a
diagram-guided kernel called FlashSign. It identifies the **special function unit**
(softmax's exponential) as the bottleneck of standard attention. ✅

The caveat matters more than the number: FlashSign is faster because it **replaces
SoftMax with an L² norm** — a different attention operator, not a faster implementation
of the same one. So the demonstrated value of the diagram method there is *guiding a
change of architecture toward one that is cheaper on the hardware*, not *making a fixed
architecture run faster*. Anyone citing "3.6×" as evidence that diagrams speed up
existing models is misreading it.

### Does this bear on our ~3% MFU?

Partly, and in a way worth taking seriously despite the absence of validation. The
repo's measured profile — no cuBLAS GEMM among the top kernels, three hand-written
Futhark kernels at ~35% of kernel time — is the kind of finding the `2mkn` accounting
plus the `M`-parameterized transfer model is designed to *predict*: which operations are
compute-bound, which are transfer-bound, and what tiling makes the difference.

That analysis is worth doing here **by hand, on paper, from the existing profile**, and
it needs neither pyncd nor this paper's category theory to do it. The contribution is a
discipline, not a tool. See §7 item (b1).

## 5. Questions 3–5 — portability, GLA, gradients

**Portable in principle, empty in practice.** pyncd's README states PyTorch is an
**optional** extra needed only "for compilation to executable models" — the core
algebraic framework does not require it ✅. The repo is organised as `data_structure`
(Category, Operators), `construction_helpers`, `data_transfer`/`websocket_transfer`,
`torch_compile`, `display`, `term_utilities`, `graphs`, `solver`, `deepseek` ✅ — so a
hypergraph IR (`graphs`) does sit between the algebra and the emitter, and a Futhark or
Haskell backend would mean writing a new emitter rather than forking the framework. But
tsncd is rendering-only ✅, so there is no second implementation to read as a spec, and
the README mentions **no** gradients, autodiff, FLOP counting, cost modelling,
benchmarking, or performance measurement anywhere ✅.

**GLA: nothing.** No linear/gated-linear/recurrent content in the paper ✅, and pyncd's
examples are attention, convolution, transformer encoder/decoder, and DeepSeek-V3
(MoE + multi-head latent attention) — all softmax ✅. The question this repo would
actually want answered — can the chunked/parallel/recurrent equivalences of GLA be stated
as morphism identities and checked mechanically? — is not addressed anywhere in this
lineage. This repo's own `FormalTransformer/Attention/Linear.agda` and the "proved
cache-run law" comment at `backend/gpu/Main.hs:1446` are already closer to it than the
paper is.

**Gradients: a correction.** My first pass through this review asserted the whole lineage
is forward-pass only. That is **wrong for the predecessor.** The TMLR paper
[arXiv:2402.05424](https://arxiv.org/abs/2402.05424) states: *"Finally, I examine
backpropagation using neural circuit diagrams. I show their utility in providing
mathematical insight and analyzing algorithms' time and space complexities."* ✅

So the accurate picture is:

| artifact | differentiation |
|---|---|
| Neural Circuit Diagrams (TMLR 2024) | **examines backprop diagrammatically** ✅ |
| FlashAttention on a Napkin (2412.03317) | forward-pass only ✅ |
| Weaves/Wires/Morphisms (2604.07242) | not formalized; `Para` is future work ✅ |
| pyncd implementation | no autodiff ✅ |

This is the one place the lineage is stronger than the headline paper suggests — and it
still does not reach our failure mode. A diagrammatic treatment that yields "mathematical
insight" into backprop is a human reasoning aid, not a checker, and it is not connected
to any tool that could compare a hand-written Futhark pullback against its forward pass
element-wise. The practice that actually caught our bug — element-wise gradient
comparison against a reference — remains the only thing that would have.

## 6. Question 6 — repetition rising while perplexity improves

The fan-out returned nothing on this; searched separately. The literature is clear and it
directly contradicts the framing that this is a defect.

- **Holtzman et al., "The Curious Case of Neural Text Degeneration"**
  ([arXiv:1904.09751](https://arxiv.org/abs/1904.09751)): maximization-based decoding
  produces degeneration, and *the probability of a repeated phrase increases with each
  repetition* — a positive feedback loop, independent of model quality.
- **Basu et al., "Mirostat" (ICLR 2021)**
  ([arXiv:2007.14966](https://arxiv.org/abs/2007.14966)): "we experimentally show that
  cross-entropy (log of perplexity) has a near-linear relation with repetition", and
  repetition is "mostly independent of the sampling method, but slightly dependent on the
  LM used". Crucially: **"for low values of k and p, perplexity drops significantly with
  generated text length and leads to excessive repetitions (the boredom trap)"**, while
  large k leads to incoherence (the confusion trap). Appropriate `k` is model-dependent,
  and "even for a fixed value of p or k, the generated text can have varying statistical
  properties."

**Lower cross-entropy therefore predicts *more* repetition, mechanically.** A model that
improves on held-out loss and simultaneously produces more repetitive free-running text
at a fixed `k` is behaving exactly as the literature says it should. This is not a
defect, and it is not evidence of a training problem.

The standard diagnostic is to vary the decoding parameters and measure; the standard
fixes are nucleus/top-p sampling (Holtzman), adaptive-`k` feedback control (Mirostat), or
an explicit repetition penalty.

**This repo's own measurements confirm it.** Two 81-draw sweeps were run for this review
(details and raw numbers in `run/generation-samples.md`), scoring unigram repetition
`rep1 = 1 − distinct/total words` over the continuation only.

Repetition falls monotonically as truncation is relaxed, in **both** models:

| arm | bpe100m @16% | bpe10m @100% |
|---|---|---|
| E greedy `t=0` | 0.698 | 0.444 |
| A shipped `t=0.8 k=40` | 0.410 | 0.384 |
| C `k=200` | 0.392 | 0.328 |
| B `t=1.0 k=40` | 0.330 | 0.281 |
| D untruncated | **0.201** | **0.254** |

Two findings dominate everything in the samples log:

1. **Seed noise exceeds every checkpoint-to-checkpoint difference ever recorded.** Within
   the shipped setting on the anchor prompt, 8 seeds give rep1 from 0.350 to 0.629. The
   single logged step-56,789 draw — described in the log as the worst degeneration so far
   — scores 0.406, which is the **least repetitive of the 8 draws** available from that
   very checkpoint. The nine single-draw comparisons in `run/generation-samples.md` were
   measuring the PRNG, not the model.
2. **Finishing training does not fix it.** The fully-trained bpe10m model
   (1,833,157/1,833,157 updates) repeats essentially as much at the shipped setting as
   the 16%-trained bpe100m: 0.384 versus 0.410, with overlapping ranges (0.214–0.615 vs
   0.296–0.629). Training progress is not the variable; the truncation is.

Within-sample entropy is also flat (4.03 → 3.97 nats from first to second half), so the
*boredom trap* — Mirostat's within-sample perplexity collapse at low `k` — is **not** the
mechanism here. The mechanism is simply that `k=40` sits at the model's effective support
and discards ~25% of the mass on every step.

## 7. Ranked recommendations

### (a) Justified by this paper

**None.** The paper has no measured result, no cost model, no gradient treatment, no
GLA content, and no non-PyTorch backend. Adopting anything from it into this codebase
today would be cargo-culting the aesthetic of formality this repo already has more of.

The one thing worth keeping is a reading note: *if* the Haskell↔Futhark layout
correspondence is ever formalized, the axis-stride category is the right vocabulary for
it (§3).

### (b) Justified by other literature or by measurement

**b0. Change the sampling protocol — do not change the model.** (Highest value, zero
risk, already measured.) `TOP_K=40` against a vocabulary of 32,768 is aggressive: the
model's measured mean next-token entropy is ~3.6 nats ≈ 37 effective tokens, so k=40 sits
right at the support and discards ~25% of the probability mass on average. Report the
median of ≥8 seeded draws with a repetition metric, never a single draw with a prose
assessment. Justified by Holtzman, Mirostat, and this repo's own sweep.

**b1. Do the arithmetic-intensity analysis on paper for the three hot Futhark kernels.**
Use `2mkn` for the contractions and the `M`-parameterized transfer form to predict which
of the three is transfer-bound. Costs an afternoon, no dependencies, no rented GPU. The
unvalidated status of the model (§4) means treat the output as a hypothesis to check
against the existing profile — which is exactly what the source paper says to do.

**b2. Add `TOP_P` as a generation-only env knob** beside `TEMPERATURE`/`TOP_K` in
`generate` (`backend/gpu/Main.hs`). ~10 lines in `pickToken`, cannot affect training,
the checkpoint format, or `modelId`. Nucleus sampling is the standard fix for exactly the
measured failure.

### (c) Speculation — flagged as such

- **c1. Untie the output embeddings in the *next* run.** The tied head is a per-row-
  rescaled symmetric Gram matrix, so the skew part of the transition statistics is
  unrepresentable (`backend/gpu/Main.hs:214`) — a plausible structural contribution to
  repetition. Costs 25.2M params (+22%) and changes `modelId`. **Not a mid-run change**,
  and untested: the `head-probe` tied/untied A/B is the cheap way to get evidence first.
- **c2. Retarget pyncd's hypergraph IR at Futhark.** Technically open (§5), but the
  payoff is unclear and the framework generates no gradients, which is where this repo's
  risk actually lives.

### Explicitly not recommended

**Do not restart the run for any of this.** The run is 17% through ~8 days of paid GPU
time. Nothing above requires new weights: (a) is empty, (b0)/(b2) are decode-side,
(b1) is paper analysis, and (c1) is a next-run decision that should be evidence-backed
before it costs anything. The GLA gate arms (`tau=16`, `glaOutputNorm`) remain measured
losers on loss (`Config.hs:77-120`) and are unrelated to the repetition question, which
§6 shows is a decoding phenomenon.

## 8. Addendum — `deepseek-ai/deepseek-harness` and the Cordis paper

Reviewed 2026-08-14. Raised on the hunch that visible category theory might hide something
architectural. It does contain real category theory, and it contains **nothing about model
architecture** — measured below rather than assumed.

### 8.1 What the two artifacts actually are

**`deepseek-ai/deepseek-harness`** is an agent CLI (`dsh`), not a model or a training
system. Its package list is `acp api attachment boot bundle client code-runtime compaction
context core credentials e2b extensions feedback fs goal guard hooks host identity
interaction jobs llm lsp mcp plan preset runtime-diagnostics sandbox schedule sdk session
settings …` — a Claude-Code-class harness. TypeScript, MIT, homepage `deepseek.com/harness`,
self-described *developer preview* with declared compatibility-breaking changes. Created
2026-08-13; 93,244 stars / 8,538 forks at the time of this review ✅ (GitHub API).

**The category theory is one link away.** The README credits
[Cordis](https://github.com/cordiverse/cordis), "whose design is described in
[*A Programming Paradigm for Spatiotemporal Composability*](https://github.com/cordiverse/paper)"
— Yifan Shi (Peking University + DeepSeek-AI), Wei Zhang (PKU), Tianyi Cui (DeepSeek-AI),
88-page PDF, draft of 2026-08-13, distributed as a PDF in a git repo with no arXiv or venue,
and labelled a preprint under active revision ✅.

Read in full for this review. It is a serious programming-languages paper about **dynamic
composition**: loading, unloading, and rewiring components at runtime. *Temporal
composability* = a component's effects are completely revertible on removal; *spatial
composability* = a component declares its dependencies and the runtime resolves them
reactively.

### 8.2 The measured answer to "does it have transformer things"

Full-text counts over the 49,070-word PDF ✅:

| Term | Occurrences | What they are |
|---|---|---|
| `tensor`, `GPU`, `machine learning`, `benchmark`, `we measure` | **0** | — |
| `Agda`, `Coq`, `Rocq`, `Lean`, `proof assistant` | **0** | no mechanization; the metatheory is hand-written |
| `transformer` | 1 | "monad transformers" (§7.1) |
| `attention` | 1 | "limited formal **attention**" (§1.2.3) |
| `experiment` | 1 | inside a reference title, not a section |

So: no architecture content, no empirical evaluation, no mechanized proofs. The proofs are
real and on paper — recovery exactness (Thm 61), terminal recovery (Cor 62), ordering
(Thm 63), resolution coherence (Thm 64), progress (Thm 66), confluence (§4.4.5) — but
nothing is checked by a machine and nothing is measured on a computer.

Its one contact with ML is §1.2.2, *self-evolving agent harnesses*: a harness that
generates and deploys modifications to its own components while continuing to serve
requests, for which a full-process restart is the current workaround. That is a claim
about **the agent editing this repo, not the model inside it.**

### 8.3 Where the category theory actually sits

§2 is a **background recap**, not the contribution: Moggi's monads, Plotkin–Power algebraic
effects and Plotkin–Pretnar handlers, Uustalu–Vene comonads for context-dependence, and
Gaboardi et al. graded coeffects over a pre-ordered semiring `(S, ≤, +, ×, 0, 1)` ✅.

The paper's own construction is **not** categorical. It is an operational calculus over a
recursive context type

```
Γ∞ := μΓ. Γ × (Γ → Γ) × Σ          -- state × accumulator-of-inverses × coeffect context
```

with transformation monoids `𝔐(a)` and an observational equivalence `≃` defined by *tests*
over a key's operations (Def. 34; Lemma 35: indistinguishability is the coarsest relation
the operations respect). That is state and process theory. It is not an algebra of tensor
programs, and unlike arXiv:2604.07242 it does not claim to be.

### 8.4 The single overlap — where this repo is already ahead

Page 8, in the background section: *"the Stream comonad `D(X) = ℕ → X` models dependence on
temporal data."* That is the closest this paper comes to a sequence model, and it is a
citation of Uustalu & Vene (2008), not a contribution ✅.

This repo already carries the sharper form of it:

- `FormalTransformer/Enriched/Bradley.agda` — `Prefix`, `PrefixObject A cutoff`,
  `BoundedPrefix`, with identity and composition constructed and proved
  (`identityPrefix`/`composePrefix`, `identityBounded`/`composeBounded`). This is the
  **bounded**-prefix category, which is what `contextSize = 256` actually is; the stream
  comonad `ℕ → X` is unbounded and would have to be cut down to say the same thing.
- `FormalTransformer/Language/Autoregressive.agda` — `StateAlgebra A W`,
  `ProperStateAlgebra`, `Distribution`, `Normalization` over a `Semiring`: the algebra of
  autoregressive state, i.e. the structure a comonad would be introduced in order to get.

So the hunch inverts. On the model side there is nothing here we do not have, and the one
point of contact is a place this repo is already further along.

### 8.5 What the paper has that we don't — and why it still doesn't apply

**Graded coeffects.** Grading tracks *usage* over a semiring: `0` unused, `1` linear, `n`
bounded, `∞` unrestricted. This repo uses `Semiring` for weights, not for usage, so this is
a genuine absence. The tempting target is the arena that never frees intra-step (~20 GB at
bpe100m micro 8). It does not connect: buffer liveness there is the Futhark compiler's job,
graded coeffects are a static discipline for a source language's binders, and nothing in
this lineage compiles to Futhark. No path exists from the paper to that bug.

**Revertible effects.** "A component's teardown is derived from its loading rather than
written alongside it" is a good discipline. Checked against this project's actual
reliability failures rather than hypothetical ones — the `piece_ce_bwd` CUDA miscompile
(correct loss, garbage gradient), the boxed-list memory wall at 115M, the quadratic corpus
planner, `rsync --files-from` silently dropping recursion — **none is a dynamic-composition
failure and none would have been caught.** The analogy is available and it is not worth
forcing.

### 8.6 Recommendation

**Adopt nothing.** Same verdict as §7(a), for a different reason: arXiv:2604.07242 is in
this field and has no measured result; this one has real theorems but is in another field
entirely.

Two things worth *knowing* rather than adopting:

1. If the tooling side of this repo ever grows a plugin surface — the cron
   pull → measure → append pipeline is the nearest thing to one — then registration that
   carries its own inverse (`ctx.effect()`) plus declared dependencies (`inject`) is the
   right shape, and Cordis is a working reference implementation of it with proofs
   attached. A tooling decision, not a model one.
2. `dsh` is an MIT-licensed agent harness in developer preview. Whether it is worth
   evaluating as a driver for the box workflow is a question about our tools, and is
   unrelated to everything else in this document.

## 9. Addendum — GLM-5.3

Reviewed 2026-08-14 (release day). Raised on the report that the new model is strong and
"the small version very powerful"; answered the same way as §8 — by checking what the
artifact actually is.

### 9.1 What shipped

GLM-5.3 (Z.ai, released 2026-08-14) is **post-training only**: the company states it
keeps the **same base model as GLM-5.2** and derives every capability gain from
scaled-up post-training — SAO (an RL method for long-horizon tasks), environment
scaling with agent-generated verified task environments, and slime (open-source
asynchronous RL infrastructure). Weights are staged, ~2 weeks out at review time.

**No small variant exists in any coverage checked** (launch coverage, the release
tracker, Hugging Face). The GLM small-model lineage is GLM-4.5-Air (106B total / 12B
active); nothing smaller than the 744B flagship is part of the 5.3 release as of today.
The "powerful small version" could not be substantiated.

### 9.2 The architecture lineage, and why none of it transfers here

The base (from GLM-5/5.2, verified against the GLM-5 technical report coverage and
Raschka's architecture note): 744B-total / ~40B-active MoE (256 routed experts, 8
active + 1 shared), 78 layers, hidden 6,144, MLA, DeepSeek Sparse Attention (a
lightweight indexer scores all prior tokens and keeps the top 2,048), **IndexShare**
(a `full, shared, shared, shared` layer cycle reusing the indexer's token selections,
justified by the measured 70–100% overlap of adjacent-layer selections; 2.9× per-token
FLOP reduction at 1M context), an MTP layer for speculative decoding, 1M-token context.

Every one of these targets **serving a ~million-token context at ~trillion scale**. At
115M dense parameters and `contextSize = 256`, sparse attention selects from a window
smaller than its own top-k, MoE and MLA solve memory problems this model does not have,
and post-training presupposes a finished base model.

Two things worth keeping, honestly labelled:

- **A structural rhyme, not a result.** IndexShare's one-full-attention-layer-per-four
  cycle is the same shape as this repo's `kindOf` rule (softmax every fourth layer, GLA
  otherwise) — and Z.ai's justification method (measure cross-layer redundancy first,
  then formalize the sharing) is this repo's own measure-first discipline applied at
  744B. Nothing to adopt; mildly confirming of the hybrid layout's shape.
- **The one theorem-shaped import: speculative-decoding unbiasedness.** MTP-style
  drafting is only sound because the accept/reject step provably preserves the target
  distribution exactly. That is a distribution-transformer theorem and would sit
  naturally beside the truncation operators in
  `FormalTransformer/Language/Decoding.agda` — but it buys decode *speed*, and this
  repo's measured generation problem was decode *distortion*. Deferred until decode
  speed matters.

### 9.3 Recommendation

**Adopt nothing**, same verdict as §7(a) and §8.6, for a third distinct reason: this
release's gains come from post-training infrastructure downstream of a base model, and
the base's architectural choices answer scale problems this project does not pose.
